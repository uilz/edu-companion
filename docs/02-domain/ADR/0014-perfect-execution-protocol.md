# ADR 0014: Agent 完美执行协议

> 状态：已生效  
> 日期：2026-07-09  
> 范围：所有涉及认知数据系统、核心算法、schema 变更、服务层改造的任务

## 背景

在多 Agent 协作和快速迭代过程中，出现为实现速度而牺牲设计完整性、测试覆盖和文档一致性的情况。本协议定义一套硬性流程，确保复杂任务能够"想清楚、写清楚、测清楚、留痕清楚"，而非补丁式堆砌。

## 核心原则

1. **文档先行，代码后置**：任何改动必须有设计文档，用户确认后再编码。
2. **任务拆小，验收明确**：大任务拆为垂直切片，每片有明确输入、输出、验收条件。
3. **测试驱动，层级覆盖**：单元、集成、端到端、回归四层测试缺一不可。
4. **关键节点 checkpoint**：schema、算法、service 迁移完成后必须单独验证。
5. **架构决策留痕**：重大决策写入 ADR 或设计文档，禁止口头/隐式约定。
6. **用户作为最终 gate**：架构方向、schema 变更、模型替换必须经过用户确认。
7. **一次只做一件事**：不并行多个大改造，聚焦一个任务直到完整收尾。

## 执行流程

### Phase 1: 设计文档

1. 在 `docs/temp/<任务编号>-<主题>.md` 创建设计文档。
2. 文档必须包含：
   - 问题定义与背景
   - 至少 2 种方案对比（含优劣、风险）
   - 推荐方案及理由
   - 关键算法公式或伪代码
   - Schema / 接口变更清单
   - 测试策略（正常、边界、异常）
   - 风险点与回滚方案
3. 设计文档完成后通知用户 review，确认后再进入 Phase 2。

### Phase 2: 任务拆解与跟踪

1. 使用 `TaskCreate` 创建主任务和子任务。
2. 每个子任务必须包含：
   - 明确范围
   - 验收条件
   - 依赖的前置子任务
3. 子任务状态必须及时更新（`pending → in_progress → completed`）。

### Phase 3: 编码与验证

每个子任务完成后必须：

1. 编写/更新单元测试并跑通。
2. 编写/更新集成测试并跑通。
3. `git diff` 自审，确保没有无关改动、临时文件、调试代码。
4. 调用 `TRAE-code-review` Skill 进行代码审查（复杂逻辑时）。
5. 更新相关文档或添加 TODO 标记待更新项。

### Phase 4: 集成与端到端验证

1. 主任务完成后：
   - 跑全量相关测试。
   - 执行 `rebuild.sh` 拉起前后端。
   - 通过浏览器或 MCP 工具验证关键路径。
2. 记录验证结果到设计文档或任务总结。

### Phase 5: 收尾与提交

1. 处理 `docs/temp` 文档：
   - 若设计稳定，合并到 `docs/adr/` 或 `docs/modules/`。
   - 若仍属临时方案，保留在 `docs/temp` 并标记状态。
2. 清理临时文件、测试脚本按规范放入 `scripts/test/<任务编号>/`。
3. `git add` 只添加相关文件，避免混入其他 agent 的改动。
4. 撰写清晰 commit message 后提交。
5. 通知用户任务完成及关键变更点。

## 禁止行为

- 不写设计文档直接编码。
- 用一个临时补丁绕过设计问题。
- 保留两套数据或逻辑并行存在。
- 只改调用点不改底层 schema/模型。
- 跳过低层级测试直接端到端。
- 把未经验证的改动直接 commit。

## 适用例外

- 纯文档整理、拼写修复、单文件简单重构可跳过完整流程。
- 紧急线上 bug 修复可先补丁止血，但必须在 24 小时内补设计文档和回归测试。
