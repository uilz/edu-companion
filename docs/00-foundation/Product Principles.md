# 🍎 Design Principles

> **苹果果设计原则**
>
> **Version 1.0**
>
> 5 条核心设计原则。遇到设计冲突时，用它们做快速决策。
>
> 它们不是功能规范，而是判断标准——当两个方案看起来都合理时，哪一条原则更符合，就选哪个。
>
> 优先级：从上到下。上优先于下。

---

## 原则一：AI First

**苹果果不是把 AI 加进旧产品，而是从 AI 出发重新定义学习。**

所有功能设计，默认以 AI 为核心交互方式。不是"加一个 AI 按钮"，而是"AI 是默认体验"。

这意味着：
- 用户打开产品，AI 已经准备好了建议
- 不是用户去"使用 AI"，而是 AI 在理解用户
- 所有后台能力（Knowledge Graph、Cognitive Engine）通过 AI 表达，不通过 UI 控件

违反此原则的例子：
- 让用户在 Dashboard 里手动筛选数据 → 应该由 AI 推荐
- 让用户在多个模块之间选择 → 应该由 AI 决定路径
- 把 AI 放在"AI 助手"子页面 → AI 应该在首页

---

## 原则二：Learning First

**技术永远服务学习，不是反过来。**

任何技术决策、架构设计、功能实现，最终判断标准只有一个：它是否让学习体验更好？

这意味着：
- 如果 DDD 分层让 Session 加载慢了，简化架构
- 如果 Event Bus 异步让用户感知到延迟，改为同步
- 如果 Knowledge Graph 的计算开销影响 Today 页面的响应速度，降低复杂度
- 技术先进性不能成为牺牲学习体验的理由

违反此原则的例子：
- "因为这个模式很优雅，所以我们要用" → 不充分
- "因为业界都这么做" → 不充分
- "因为这样代码更好维护" → 不充分（除非能说明如何间接改善学习体验）

---

## 原则三：Outside In

**从用户感受到的体验出发设计，不是从系统内部结构出发。**

设计任何功能时，第一句话必须是用户视角："用户打开苹果果，他看到……"
而不是："我们需要一个 XXX 模块……"

这意味着：
- 用户只应该感受到三件事：AI 记得我、AI 知道我的困难、AI 知道下一步
- 后台可以很复杂，但用户永远只看到一个简单的界面
- 先定义用户旅程，再定义数据模型
- 先定义验收标准，再定义 API

违反此原则的例子：
- "我们需要一个 Knowledge Graph 管理页面" → 用户不需要管理知识图谱
- "Dashboard 可以展示很多数据" → 用户不需要看数据，需要看建议
- "这个 API 返回了完整的学习者模型" → 用户不需要看这个

---

## 原则四：Consistency

**苹果果在任何地方都应该是"同一个苹果果"。**

从 Today 到 Session 到 Growth 到 Profile，用户应该感受到一致的人格、一致的交互模式、一致的信息结构。

这意味着：
- AI 的语调在所有页面保持一致（研究伙伴，不说教、不命令）
- 交互模式一致（AI 主动建议，用户确认/执行）
- 视觉语言一致（设计系统统一）
- 信息层次一致（Today 的问题 → Session 的过程 → Growth 的结果）

违反此原则的例子：
- Today 是 AI 建议模式，Session 变成自由聊天模式
- 界面在不同页面切换风格
- 同一类信息在不同页面用不同的术语

---

## 原则五：Never Start Over

**苹果果永远记得昨天。**

用户每次打开苹果果，AI 都应该表现出"我知道你昨天学到了哪里"，而不是从零开始。

这意味着：
- Today 的第一句话永远是"我们继续昨天"，不是"有什么可以帮你"
- Session 结束后的 Learner Model 更新必须被下一个 Session 使用
- 成长是连续的，不是每天重置
- 聊天记录不是产品记忆，Learner Model 才是

违反此原则的例子：
- 每次打开都让用户选择"今天想学什么"
- Session 与 Session 之间没有信息传递
- AI 不记得用户上周的困难和进步
- 把产品的"记忆"等同于聊天历史记录

---

> **快速决策卡：遇到设计冲突，从上到下检查。哪一条原则给出更明确的答案，就按哪一条执行。**
