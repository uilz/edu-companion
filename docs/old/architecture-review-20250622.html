进程重启后，内存中的事件丢失

  PUB2["发布者"]

  classDef deep fill:#0f172a,color:#fff,stroke:#0f172a
  class BUS2 deep

events 表已有的 status 字段（pending→processing→done）
直接作为 EventBus 的持久化队列

问题

EventBus 是 asyncio.Queue 内存实现。进程崩溃事件丢失。events 表有持久化和 status 状态机，但 EventBus 没有消费它。两套机制各跑各的。

方案

EventBus 改为消费 events 表。publish() → INSERT 到 events 表，后台轮询 pending 事件分发。events 表已有的 status 状态机直接复用。

收益

  • 事件不丢失：进程崩溃可恢复
  • 删除内存队列与 events 表的双写
  • 事件可审计、可重放
  • Harness 测试：直接查 events 表验证

问题

CognitiveNode 包含 15 个子系统，接口宽度约 50+ 字段。对话注入时只需 mastery+belief，但不得不加载全部。大部分子系统从未被实际决策使用。

方案

拆分为 MasteryAtom（核心）+ 按场景懒加载的 Profile（PracticeProfile / PlanningProfile / DiagnosisProfile）。API 按需查询。

收益

  • 接口缩小：50+ 字段 → 5 核心字段
  • Leverage：每个场景只学自己的接口
  • AI 个性化：按场景注入精确数据
  • Harness 可独立测试各 Profile

Top Recommendation

#1 domain/ 层泄漏修复

这是所有后续优化的前提。当前 domain/cognitive/ 和 domain/auth/ 直查数据库，破坏了分层契约。 修复后，所有模块通过 shared/protocols/ 的 Protocol 定义依赖 —— 这是 Harness 可测试性的基础。

解决了这个泄漏，Candidate #2-#7 的深化才有干净的 Seam 可以走。

建议执行顺序

  1. domain/ 泄漏修复 — 基础设施就位
  2. 对话系统双路径合并 — 删除旧 ConversationServiceImpl
  3. 练习系统深化 — 14 文件 → PracticeEngine
  4. 知识模型统一 — 三套 → 单一 KnowledgeAtom
  5. EventBus 可靠化 — 内存 → events 表驱动
  6. services/ 层精简 — 删除 pass-through
  7. CognitiveNode 场景化拆分 — 按需加载
