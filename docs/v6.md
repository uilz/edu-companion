# 智能伴学系统 6.0 phase1 完整优化方案

> **版本**：6.0  
> **目标**：修复底层数据架构断裂，建立认知原生数据底座，打通模块联动，为后续智能功能提供坚实基础。  
> **原则**：不新增用户功能，只做架构治理、数据统一和关键链路贯通。

---

## 一、整体现状与核心问题

当前系统（79 个接口、18 张表）功能完整，但存在三个结构性断裂：

1. **双轨树并存**：`conversation_partitions/domains/topics` 与 `cognitive_nodes` 两套层级独立运行，侧边栏、分类器、秘书各看各的数据源。
2. **消息存储无认知锚点**：消息仅以 `response_blocks` 形式存储，缺少语义向量、认知节点关联、细粒度标注，秘书和分类器无法利用对话历史进行深度推理。
3. **模块联动靠硬编码调用**：缺少事件总线，分类确认、练习提交等关键节点无法自动触发秘书诊断、可见性更新、认知状态刷新。

此外，分层检索、边信任度惰性更新、临时会话等高级设计尚未完全落地。

---

## 二、优化目标

- **统一写入**：所有知识树节点写入 `cognitive_nodes`，旧表逐步废弃。
- **认知化消息存储**：建立 `messages` 表，承载消息语义向量、认知关联和标注。
- **事件驱动联动**：基于 `cognitive_events` 表实现异步解耦的模块通信。
- **性能与可维护性**：建立必要的索引，完善日志，统一错误处理，集中 SQL 管理。
- **功能补齐**：实现分层检索、边信任度惰性更新、临时会话模式、对话摘要与长上下文支持。

---

## 三、详细实施方案

### 阶段 1：数据模型重构（核心基础）

#### 1.1 补全 `cognitive_nodes` 字段与索引

```sql
ALTER TABLE cognitive_nodes ADD COLUMN IF NOT EXISTS is_visible BOOLEAN DEFAULT false;
ALTER TABLE cognitive_nodes ADD COLUMN IF NOT EXISTS node_type VARCHAR(50) DEFAULT 'explicit';
ALTER TABLE cognitive_nodes ADD COLUMN IF NOT EXISTS created_by VARCHAR(50) DEFAULT 'system';
ALTER TABLE cognitive_nodes ADD COLUMN IF NOT EXISTS description TEXT;
ALTER TABLE cognitive_nodes ADD COLUMN IF NOT EXISTS metadata JSONB DEFAULT '{}';

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_cn_parent ON cognitive_nodes(user_id, parent_id) WHERE deleted_at IS NULL;
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_cn_level ON cognitive_nodes(user_id, level) WHERE deleted_at IS NULL;
```

#### 1.2 新建 `messages` 表

```sql
CREATE TABLE messages (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    user_id UUID NOT NULL,
    role VARCHAR(20) NOT NULL,
    content TEXT NOT NULL,
    content_blocks JSONB DEFAULT '[]',
    embedding VECTOR(1536),
    cognitive_node_ids UUID[] DEFAULT '{}',
    cognitive_annotations JSONB DEFAULT '[]',
    summary TEXT,
    token_count INT,
    created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_msg_conv ON messages(conversation_id, created_at);
CREATE INDEX idx_msg_embedding ON messages USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100) WHERE embedding IS NOT NULL;
```

#### 1.3 补全 `knowledge_edges` 边表

```sql
ALTER TABLE knowledge_edges ADD COLUMN IF NOT EXISTS trust_score FLOAT DEFAULT 0.5;
ALTER TABLE knowledge_edges ADD COLUMN IF NOT EXISTS last_evaluated_at TIMESTAMPTZ DEFAULT now();
ALTER TABLE knowledge_edges ADD COLUMN IF NOT EXISTS edge_status VARCHAR(30) DEFAULT 'suggested';
```

#### 1.4 完善 `cognitive_events` 事件表

```sql
CREATE TABLE IF NOT EXISTS cognitive_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    payload JSONB NOT NULL DEFAULT '{}',
    processed BOOLEAN DEFAULT false,
    created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_ce_unprocessed ON cognitive_events(processed, created_at);
```

#### 1.5 数据迁移

- 编写一次性脚本，将 `conversation_partitions` → `conversation_domains` → `conversation_topics` 提升为 `cognitive_nodes` 记录（`node_type='migrated'`）。
- 将 `conversation_response_blocks` 内容逐条转为 `messages` 行，保留原始时间戳和顺序。
- 更新 `conversations.primary_node_id` 外键，补全 `conversation_node_links`。
- 迁移后运行一致性校验脚本。

### 阶段 3：消息存储重构与认知锚定

#### 3.1 改造消息写入

- 消息发送接口改为写入 `messages` 表，同时生成纯文本、embedding（异步）、token 估算。
- 保留 `content_blocks` 存储富文本，`content` 存储纯文本用于检索和摘要。

#### 3.2 分类确认后回写认知关联

在分类器用户确认归属后，更新对应 `messages.cognitive_node_ids`（包含 topic 及 atom 节点）。

#### 3.3 LLM 异步认知标注

- 后台任务对用户消息进行分析，标注认知行为（`question`、`self_explanation`、`confusion` 等）和质量（`correct`、`misconception`），写入 `cognitive_annotations` 字段。
- 实现降级：如果 LLM 不可用，不标注，不影响主流程。

#### 3.4 实现语义记忆检索

提供内部函数 `search_learning_memory(user_id, query)`，基于消息 embedding 检索历史讲解内容，支持“上次讲的比喻”类查询。

### 阶段 4：事件驱动联动（模块解耦）

#### 4.1 定义事件类型与 payload

| 事件类型 | payload 关键字段 |
|----------|------------------|
| `message.classified` | message_id, conversation_id, topic_node_ids[], atom_node_ids[], mode |
| `practice.submitted` | atom_node_ids[], correctness, latency_ms |
| `node.created` | node_id, parent_id, level, created_by |
| `secretary.proposal.accepted` | proposal_id, action_type, target_node_id |

#### 4.2 实现事件写入工具函数

```python
async def emit_event(user_id, event_type, payload):
    await db.execute("INSERT INTO cognitive_events (user_id, event_type, payload) VALUES ($1,$2,$3)",
                     user_id, event_type, json.dumps(payload))
```

在分类器确认归属、练习提交、节点创建、提案采纳等代码点调用。

#### 4.3 实现事件消费者（后台异步任务）

在 FastAPI lifespan 中启动 `asyncio.create_task(consume_events())`，轮询未处理事件并分发到对应 handler：

- `handle_message_classified`：更新消息认知关联、节点可见性、祖先级联可见、dialogue_contexts。
- `handle_practice_submitted`：更新贝塔分布参数、mastery、activation。
- `handle_node_created`：触发秘书波纹扩展建议（异步）。
- `handle_proposal_accepted`：执行秘书提案对应的图谱操作（创建节点、添加边等）。

#### 4.4 可见性级联更新

实现 `cascade_ancestor_visibility(node_id)`：递归向上查找父节点，若其不可见则设为可见，直到根或已可见节点。

### 阶段 6：秘书系统联动增强

#### 6.1 结构扩展建议

- 不再独立维护触发条件，改为消费 `message.classified` 事件，统计父节点下可见子节点的活动频率，达标则生成“展开更多专题”提案。

#### 6.2 波纹边确认

- 消费 `node.created` 事件，对新节点进行语义邻居检索，生成 `knowledge_edges` 记录。
- 对 `pending_confirm` 边，在用户学习间隙生成确认提案（附带简短理由）。

#### 6.3 深度沉浸延后处理

- 会话结束或用户空闲时，读取分类器写入的待处理跨主题候选，生成“本次对话涉及多个话题，是否关联？”的确认提案，用户确认后批量添加辅助归属。

---

### 阶段 7：性能与运维优化

#### 7.1 查询性能

- 使用 `EXPLAIN ANALYZE` 审查所有高频 SQL，确保使用新索引。
- 侧边栏懒加载避免递归 CTE，单次只查直接子节点。
- 对消息 embedding 检索使用 `ivfflat` 索引并定期 `REINDEX`。

#### 7.2 日志与监控

- 关键操作（分类决策、事件处理失败、迁移进度）记录结构化日志。
- 监控事件队列长度，超过阈值告警。

#### 7.3 连接池与超时

- PostgreSQL 连接池合理配置 `min_size=5, max_size=20`。
- Redis 操作添加 1s 超时与重试，不可用时静默降级。

#### 7.4 代码质量

- SQL 语句集中到各模块 `queries.py`，统一参数化。
- 定义 `AppError` 异常体系，FastAPI 全局异常处理返回标准 JSON。
- 使用 Pydantic Settings 管理配置，支持 `.env` 与环境变量。

---

### 阶段 8：高级特性补全

#### 8.1 边信任度惰性更新

- 每次读取 `knowledge_edges.trust_score` 时，根据 `last_evaluated_at` 计算衰减并写回。
- 学习活动触发证据增强（`trust_score += (1 - trust_score) * evidence`）。

#### 8.2 临时会话模式

- `conversations` 表增加 `is_temporary` 字段，临时会话不创建任何 `cognitive_node`，不写 `conversation_node_links`。
- 前端提供“保存”按钮，触发秘书协商创建节点并转为常规会话。
- 每小时定时任务清理 48 小时未活动的临时会话及关联消息。

#### 8.3 对话摘要与长上下文

- 创建 `conversation_summaries` 表，每 10 轮对话生成一次摘要，存储涉及的知识点。
- 构建 LLM 上下文时，使用“最近 5 轮完整消息 + 之前摘要”的组合方式，控制 token 消耗。

## 五、风险与回滚

- **数据迁移风险**：事务内执行，提供回滚脚本；旧表保留至少 2 周。
- **性能退化**：每次变更后进行基准测试对比。
- **业务中断**：采用双写模式过渡，确认新逻辑稳定后再停止写旧表。
- **事件积压**：监控队列长度，设置告警；消费者横向可扩展（多 worker）。

该方案完成后，智能伴学系统将拥有一个认知原生的数据底座，所有高级功能（动态诊断、自适应路由、长期记忆）将能够真正融合为有机整体，实现从“对话工具”到“智能伴学管家”的质变。
